# ADR 0007: Tactical Design Is Conditional and Claim-Led

- Status: Accepted
- Date: 2026-08-17
- Supersedes: the unconditional absence of a tactical-design workflow stage in [ADR 0004](0004-model-ready-enters-codify-directly.md)
- Extends: artifact lifecycle and closure in [ADR 0005](0005-event-storming-minutes-and-current-models.md), and Guard authority and unit seeding in [ADR 0006](0006-guard-is-a-semantic-structure-review.md)
- Draft timing, implementation reconciliation, and artifact authority refined by: [ADR 0008: Design Artifacts Are Falsifiable Candidates](0008-design-artifacts-are-falsifiable-candidates.md)

## Context

EventStorming currently confirms business language, ownership, Aggregates, lifecycle, constraints, and cross-context meaning, then hands the result directly to Codify. Canonical Models describe Aggregate boundaries but do not make each Root's business capabilities or required `fact -- Command --> capability` mappings checkable. Complete collaboration is present only as a business EventStorming flow; transaction, state, concurrency, event-publication, failure, and recovery ownership can remain implicit.

That gap permits two independently reasonable steps to compose badly. A user can accept each business concept while Codify invents an unfamiliar coordination mechanism, transaction boundary, or event order during implementation. Requiring a full design phase for every change would replace that failure with unnecessary ceremony and duplicate reversible choices that Codify can safely make.

## Decision

EventStorming normalizes Commands by the intent chosen by a Bounded Context-local Role or required by an established fact, then projects **Role-to-Command permissions**, **Aggregate Capabilities**, and **Event-triggered Commands** into each affected canonical Model. Every in-scope state-changing Command maps to one or more capabilities or explicit coordination, and every new or changed capability names its source Command or Commands. One capability is one stable Root operation that guides its intention-revealing Domain method surface; pre-state, success, rejection, and timing branches remain lifecycle, invariant, or policy meaning rather than separate capability rows. Capabilities state only common required authoritative facts, guaranteed business result, and stable rejection. They prescribe neither signatures nor exact method counts, handlers, transport, transactions, retry mechanisms, packages, persistence, or Application orchestration.

EventStorming minutes retain complete low-resolution business-success diagrams and no parallel Command mapping table. A business Role appears inside its Bounded Context and outside Aggregates; its Command is the labeled arrow into a Root-owned Capability or explicit coordination, and that target establishes a material Workshop Event. Generic preconditions, Policy nodes, permission failures, rejected or unchanged results, and Hotspots remain outside the main diagram; adverse facts remain only when they change business rights, obligations, value, or required next action. A selected local Domain Event stays distinct from its producer-owned Published Fact Contract and eventual Integration Message realization. The affected `model.md` is the sole current capability authority; every projected contract field must already be supported by a connected Workshop Event, confirmed decision, assumption, or other evidence in the confirmed minutes. An event-triggered Command records `selected Domain Event or Published Fact Contract -- Command --> Aggregate Capability or explicit coordination`, plus its required business outcome. Existing capability and reaction tables remain readable authority and migrate only when EventStorming next changes their Model; no format-only Model revision is created.

Tactical Design is conditional on a real Design Delta. A Design Delta exists when realization creates or changes material Aggregate/context coordination, transaction ownership, state/checkpoint ownership, concurrency control, event-publication timing, failure/recovery responsibility, semantic ports, or another durable Interface boundary not already accepted. No Design Delta creates no Tactical Design artifact; ordinary reversible work inside established seams continues directly to Codify.

One material delta is stored at `docs/ddd-expert/tactical-design/<slug>.md`. The record is scoped to an implementation slice, may reference multiple EventStorming iterations and Bounded Contexts, and is not created mechanically per Model or meeting. `model.md` owns current Bounded Context business authority, Role-to-Command permissions, Aggregate Capabilities, and event-triggered Commands. A Tactical Design `draft` owns only a falsifiable exploration candidate; its reconciled `ready` state owns the accepted collaboration design for the slice. ADRs own hard-to-reverse project decisions and rationale; code and configuration own implementation detail.

An optional `docs/ddd-expert/context/<context-slug>/architecture.md` owns only current, durable, BC-specific software decisions that outlive one Design Delta. It is created lazily, contains one compact decision table, and links every row to its confirming Tactical Design claim. The file is optional; claim disposition is not. Every Tactical Design Claim is accounted for exactly once as `projected` or `iteration-only`. A projected claim names one owning context, action, local decision ID, and current statement or removal marker, then creates, updates, or removes that context's Architecture state in the same ready consistency write. An iteration-only claim gives a concrete reason that no BC-specific constraint survives and produces no Architecture change. The Architecture never copies Model facts, generic House Style, complete sequences, code structure, or historical rationale. A cross-context decision is projected once to the context that owns the responsibility. No root `docs/ddd-expert/architecture.md` is introduced.

A pure context rename moves its Architecture without revising decisions. A split, merge, or removal retires the old Architecture without automatically reassigning rows; any decision that must survive the new boundary is confirmed again through Tactical Design.

Each Tactical Design contains:

- the exact Design Delta, authority links, scope, and exclusions;
- a domain-object responsibility thesis and class diagram;
- live and durable state authority plus the minimal semantic result flow;
- a positive necessity proof for every proposed participant, state, event, checkpoint, or recovery mechanism;
- the fewest typed critical sequences needed to expose the normal collaboration, with a separate adverse path only when responsibility, guarantee, durable state, required next action, or visible result changes;
- transaction, concurrency, event-publication, failure, and recovery ownership only where the Design Delta actually includes them;
- changed semantic Interfaces and their connection to Aggregate Capabilities;
- non-goals, Codify discretion, the strongest credible alternative, and reasons.

The exploration draft omits final claims, Architecture disposition, and Reconciliation Evidence. After reversible implementation evidence has tested the candidate, the reconciled draft additionally contains concrete evidence, a small set of immutable `Tactical Design Claims` with record-local `TD-NNN` IDs and canonical `<record-path>#TD-NNN` keys, and one exhaustive claim-disposition ledger with exact `add`/`replace`/`remove` projections for durable claims and concrete `iteration-only` reasons for the rest.

The class diagram, responsibility table, state authority, semantic flow, and critical sequences form one system thesis rather than independent completion checklists. Sequences derive every participant and call from that thesis; the template supplies no default Repository or cross-context topology. They group technical objects by owning Bounded Context while business Roles, external authorities, and unowned external systems remain outside those boxes. Invocation arrows name receiver-visible semantic operations and replies name semantic results without forcing a final language signature or one-to-one Capability-to-method mapping. Adjacent traceability preserves only the accepted Model meaning needed to understand the Design Delta. When meaning crosses a Bounded Context, the sequence keeps the producer fact/contract, message realization, consumer translation, event-triggered Command, and target Capability distinct when each is actually selected. Analytical Workshop Events create no production event obligation. A genuinely crowded design uses the fewest readable scenario-focused diagrams and no parallel mapping table.

The record normally follows `draft -> ready -> implemented`; newer confirmed business authority or later reconciled implementation evidence may add `ready -> superseded` before implementation. Ordinary `no_design_change` is a zero-write result only when no existing draft or invalidated ready authority awaits resolution; removing such a draft returns `discarded`, while retiring such a ready record returns `superseded`. Tactical Design first restates and challenges the user's thesis, or attacks its own smallest candidate, in conversation. It writes an exploration draft only after object responsibility, state authority, semantic flow, necessity, and the challenged alternative form one coherent whole. The user may stop with that non-authoritative design-only draft. With explicit implementation authority, Codify may then test it through reversible exploration and return concrete evidence. Tactical Design reconciles related evidence as one connected design revision batch rather than patching the artifact per observation, then adds final claims and dispositions and asks the user to confirm the exact current path and fingerprint. The exact ready transition, README, exhaustive claim dispositions, matching Architecture projections, and required ADR closure are applied together; absence of implementation evidence or a projected claim without its owning Architecture write blocks the transition. Tactical Design never changes canonical Models.

Tactical Design may falsify but never silently override EventStorming authority. It gathers concrete business or strategic-structure contradictions in one temporary Model Review Batch, sweeps the current object-responsibility and state thesis for dependent hypotheses, and returns one consolidated **Model Challenge** rather than one challenge per observation. EventStorming resolves that batch one frontier question at a time and creates at most one correction draft, rewriting it until integrated confirmation; it does not create one record per question or rewrite already confirmed history. After EventStorming returns unchanged or newer ready Models, Tactical Design resumes the same draft, rebases it when the same delta remains, or discards the unconfirmed draft when the delta disappears or its implementation-slice identity is replaced. Concrete implementation evidence may drive the same draft discard while the governing Model remains unchanged. An unimplemented ready Tactical Design is never edited or discarded: with explicit confirmation, a replacement ready record supersedes it when a material delta remains, while direct retirement supersedes it against the surviving ready EventStorming authority when no delta remains. Under unchanged EventStorming authority, the retirement link says that the existing Model is sufficient; it does not imply changed business facts. Either path requires concrete evidence and replaces or removes every BC Architecture source from the stale claims in the same consistency write. Implemented records remain provenance.

Codify has two modes when implementation has an active Design Delta. Explicitly authorized reversible exploration may consume a coherent `draft` as a candidate, change only the bounded reversible scope, and return implementation evidence to Tactical Design without projecting Architecture, invoking Guard, or claiming conformance. Final realization consumes current BC Architecture plus a reconciled `ready` Tactical Design whose governing EventStorming links remain ready. For every DDD-backed implementation—including the direct EventStorming-to-Codify path—it builds a temporary scoped `model_projection_map` from implementation-shaping Model concepts and relationships to software responsibilities and actual `path#symbol` evidence. The map is many-to-many, creates no naming or method-count rule, and stays outside Models, BC Architecture, ADRs, and code. In final mode Codify also maps canonical claim keys to changed symbols in the neutral Review Handoff, but cannot edit claims or prewrite verdicts. Implemented Tactical Design records are provenance rather than current authority; superseded records are invalidated history. Evidence against Model-owned business meaning or Bounded Context, Aggregate, capability, or core-object strategic structure returns to EventStorming. A tactical collaboration, state-authority, or software-boundary alternative returns to Tactical Design only when it preserves that strategic structure.

Guard remains one fresh read-only semantic-structure reviewer. Its authority order places current BC Architecture and ready Tactical Design below Models, ready EventStorming, and accepted project constraints, but above House Style defaults and code evidence. It independently reconstructs the scoped Model projection and compares it with Codify's navigation map; the producer map is neither authority nor a verdict. Its finite units are seeded by all governing source-backed architecture responsibilities plus changed DDD-significant declarations or wiring. Guard does not parse every Mermaid arrow or create units per projection entry, arrow, file, method, layer, mechanism, or rule.

When code contradicts an accepted Tactical Design, Guard reports a violation routed to Codify. Missing or contradictory Model-owned business meaning or strategic structure routes to EventStorming. Missing or contradictory tactical collaboration authority, or an implementation need that changes collaboration, state authority, or a software boundary while preserving the current strategic structure, routes to Tactical Design. Existing `clear`, `violation`, and `evidence_gap` terminal states remain unchanged.

A clear Guard review with a complete snapshot-bound producer checkpoint closes every reviewed ready EventStorming and Tactical Design record together while leaving BC Architecture current. When no Tactical Design governed the implementation, EventStorming-only closure remains valid. Partial closure is rejected because it would claim that one part of the accepted iteration was implemented independently.

## Consequences

- Business behavior becomes inspectable at each Aggregate Root without turning Models into code designs.
- Command-to-Capability traceability guides Domain method design without multiplying capabilities by state branch or forcing a one-method signature rule.
- Business-required Event-to-Command causality remains current without a Reaction Policy abstraction or implementation wiring.
- Bounded Context ownership and receiver-visible Public Method collaboration become visible and confirmable before code is written.
- The same typed relationships remain traceable through Tactical Design, Codify, and Guard without a second long-lived model.
- Role authorization, local Domain Events, published contracts, Integration Messages, and event-triggered Commands no longer collapse into one generic handler edge.
- Tactical Design returns one settled Model problem rather than bouncing through one EventStorming record per question.
- Routine changes retain the low-cost direct Model-to-Codify path.
- Tactical Design records remain iteration-scoped; only their durable BC-owned decisions survive in optional sibling Architecture files, with no root architecture catch-all.
- A ready transition with no Architecture write now means every claim was explicitly justified as iteration-only; an explicit removal may still delete a file whose final current row was retired.
- Guard gains design fidelity without another reviewer, another verdict axis, arrow auditing, test execution, or file-by-file review.

## Verification

- Release contracts assert Aggregate Capability projection, Role permission persistence, thesis-derived Tactical Design sequences, the draft exploration/reconciliation boundary, exhaustive ready claim disposition, temporary Codify projection mapping, independent Guard reconstruction, conditional routing, lifecycle and claims, and joint closure.
- A positive Tactical Design producer fixture carries concrete implementation evidence, confirms the exact reconciled draft, and requires the matching ready record plus owning BC Architecture file to be written together; a negative fixture is otherwise valid and leaves exactly one claim unaccounted.
- A Guard behavior fixture binds one accepted claim to a concrete Application symbol and requires code drift to route to Codify.
- Claude and Codex skill and template bodies remain mirrored, and standard release validation remains green.
