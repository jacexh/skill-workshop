# ADR 0007: Tactical Design Is Conditional and Claim-Led

- Status: Accepted
- Date: 2026-08-17
- Supersedes: the unconditional absence of a tactical-design workflow stage in [ADR 0004](0004-model-ready-enters-codify-directly.md)
- Extends: artifact lifecycle and closure in [ADR 0005](0005-event-storming-minutes-and-current-models.md), and Guard authority and unit seeding in [ADR 0006](0006-guard-is-a-semantic-structure-review.md)

## Context

EventStorming currently confirms business language, ownership, Aggregates, lifecycle, constraints, and cross-context meaning, then hands the result directly to Codify. Canonical Models describe Aggregate boundaries but do not make each Root's business capabilities or required `fact -- Command --> capability` mappings checkable. Complete collaboration is present only as a business EventStorming flow; transaction, state, concurrency, event-publication, failure, and recovery ownership can remain implicit.

That gap permits two independently reasonable steps to compose badly. A user can accept each business concept while Codify invents an unfamiliar coordination mechanism, transaction boundary, or event order during implementation. Requiring a full design phase for every change would replace that failure with unnecessary ceremony and duplicate reversible choices that Codify can safely make.

## Decision

EventStorming normalizes Commands by the intent chosen by a Bounded Context-local Role or required by an established fact, then projects **Role-to-Command permissions**, **Aggregate Capabilities**, and **Event-triggered Commands** into each affected canonical Model. Every in-scope state-changing Command maps to one or more capabilities or explicit coordination, and every new or changed capability names its source Command or Commands. One capability is one stable Root operation that guides its intention-revealing Domain method surface; pre-state, success, rejection, and timing branches remain lifecycle, invariant, or policy meaning rather than separate capability rows. Capabilities state only common required authoritative facts, guaranteed business result, and stable rejection. They prescribe neither signatures nor exact method counts, handlers, transport, transactions, retry mechanisms, packages, persistence, or Application orchestration.

EventStorming minutes retain complete low-resolution business-success diagrams and no parallel Command mapping table. A business Role appears inside its Bounded Context and outside Aggregates; its Command is the labeled arrow into a Root-owned Capability or explicit coordination, and that target establishes a material Workshop Event. Generic preconditions, Policy nodes, permission failures, rejected or unchanged results, and Hotspots remain outside the main diagram; adverse facts remain only when they change business rights, obligations, value, or required next action. A selected local Domain Event stays distinct from its producer-owned Published Fact Contract and eventual Integration Message realization. The affected `model.md` is the sole current capability authority; every projected contract field must already be supported by a connected Workshop Event, confirmed decision, assumption, or other evidence in the confirmed minutes. An event-triggered Command records `selected Domain Event or Published Fact Contract -- Command --> Aggregate Capability or explicit coordination`, plus its required business outcome. Existing capability and reaction tables remain readable authority and migrate only when EventStorming next changes their Model; no format-only Model revision is created.

Tactical Design is conditional on a real Design Delta. A Design Delta exists when realization creates or changes material Aggregate/context coordination, transaction ownership, state/checkpoint ownership, concurrency control, event-publication timing, failure/recovery responsibility, semantic ports, or another durable Interface boundary not already accepted. No Design Delta creates no Tactical Design artifact; ordinary reversible work inside established seams continues directly to Codify.

One material delta is stored at `docs/ddd-expert/tactical-design/<slug>.md`. The record is scoped to an implementation slice, may reference multiple EventStorming iterations and Bounded Contexts, and is not created mechanically per Model or meeting. `model.md` owns current Bounded Context business authority, Role-to-Command permissions, Aggregate Capabilities, and event-triggered Commands. Tactical Design owns the accepted collaboration design for its slice. ADRs own hard-to-reverse project decisions and rationale; code and configuration own implementation detail.

An optional `docs/ddd-expert/context/<context-slug>/architecture.md` owns only current, durable, BC-specific software decisions that outlive one Design Delta. It is created lazily, contains one compact decision table, and links every row to its confirming Tactical Design claim. The file is optional; claim disposition is not. Every Tactical Design Claim is accounted for exactly once as `projected` or `iteration-only`. A projected claim names one owning context, action, local decision ID, and current statement or removal marker, then creates, updates, or removes that context's Architecture state in the same ready consistency write. An iteration-only claim gives a concrete reason that no BC-specific constraint survives and produces no Architecture change. The Architecture never copies Model facts, generic House Style, complete sequences, code structure, or historical rationale. A cross-context decision is projected once to the context that owns the responsibility. No root `docs/ddd-expert/architecture.md` is introduced.

A pure context rename moves its Architecture without revising decisions. A split, merge, or removal retires the old Architecture without automatically reassigning rows; any decision that must survive the new boundary is confirmed again through Tactical Design.

Each Tactical Design contains:

- the exact Design Delta, authority links, scope, and exclusions;
- one complete typed critical sequence per material success, failure, or recovery path, including rejection, timeout, or retry only when it changes ownership or guarantees;
- transaction, state, concurrency, event-publication, failure, and recovery ownership;
- changed semantic Interfaces and their connection to Aggregate Capabilities;
- a small set of immutable `Tactical Design Claims` with record-local `TD-NNN` IDs and canonical `<record-path>#TD-NNN` keys;
- one exhaustive claim-disposition ledger, with exact `add`/`replace`/`remove` projections for durable claims and concrete `iteration-only` reasons for the rest;
- non-goals, Codify discretion, the strongest credible alternative, and reasons.

Those sequences are the only persisted Model-to-design projection. They group every technical object by its owning Bounded Context in one Mermaid `box ... end`, while business Roles, external authorities, and external systems without a modeled owning context remain outside the object boxes. Every invocation arrow into or between technical participants names the receiver's `Public Method`; every reply names the returned semantic result. A Public Method is the receiver-visible callable seam, not necessarily a public network API or final language signature, and it does not force a one-to-one Capability-to-method mapping. Participant labels and adjacent traceability notes preserve each relevant Role or external authority, Command, Aggregate, Capability, selected Domain Event, Published Fact Contract, Integration Message, explicit coordination, and analytical Workshop Event with its accepted kind and name. When meaning crosses a Bounded Context, the sequence keeps the producer's Domain Event and published contract, Integration Message realization, consumer translation, event-triggered Command, and target Capability distinct. Analytical Workshop Events explain outcomes but create no production event obligation. A path gets its own diagram only when responsibility, guarantee, durable state/checkpoint, or visible outcome differs; mechanically equivalent variants share an `alt` branch or note. A genuinely crowded design uses the fewest readable scenario-focused diagrams and no parallel mapping table.

The record normally follows `draft -> ready -> implemented`; newer confirmed business authority may add `ready -> superseded` before implementation. Ordinary `no_design_change` is a zero-write result only when no existing draft or invalidated ready authority awaits resolution; removing such a draft returns `discarded`, while retiring such a ready record returns `superseded`. Tactical Design writes a complete initial draft before the first review question so the editor artifact is the shared canvas. Each turn advances one material question and adversarially tests user proposals; related tactical conclusions form one connected design revision batch, and the complete draft is redrawn only after every affected path settles. Suspected Model contradictions instead accumulate in one temporary Model Review Batch while the draft remains byte-identical. Tactical Design sweeps the complete existing design for dependent contradictions, then either resumes without EventStorming or returns one consolidated Model Challenge. When no question or batch remains, the user confirms the exact current path and fingerprint as one collaboration design. The exact ready transition, README, exhaustive claim dispositions, matching Architecture projections, and required ADR closure are applied together; a projected claim without its owning Architecture write blocks the transition. Tactical Design never changes canonical Models.

Tactical Design may falsify but never silently override EventStorming authority. It freezes its draft and returns one consolidated **Model Challenge** only after the Model Review Batch has covered every known dependent sequence, claim, Architecture projection, and material failure/recovery path. EventStorming resolves that batch one frontier question at a time and creates at most one correction draft, rewriting it until integrated confirmation; it does not create one record per question or rewrite already confirmed history. After EventStorming returns unchanged or newer ready Models, Tactical Design resumes the same draft, rebases it when the same delta remains, or discards the unconfirmed draft when the delta disappears or its implementation-slice identity is replaced. A ready Tactical Design whose governing EventStorming authority is superseded is never edited or discarded: a replacement ready record supersedes it when a material delta remains, while direct retirement supersedes it against the newer ready minutes when no delta remains. Either path replaces or removes every BC Architecture source from the stale claims in the same consistency write.

Codify consumes current BC Architecture plus a ready Tactical Design whose governing EventStorming links remain ready when the implementation has an active Design Delta. For every DDD-backed implementation—including the direct EventStorming-to-Codify path—it builds a temporary scoped `model_projection_map` from implementation-shaping Model concepts and relationships to software responsibilities and actual `path#symbol` evidence. The map is many-to-many, creates no naming or method-count rule, and stays outside Models, BC Architecture, ADRs, and code. Codify also maps canonical claim keys to changed symbols in the neutral Review Handoff, but cannot edit claims or prewrite verdicts. Implemented Tactical Design records are provenance rather than current authority; superseded records are invalidated history. If implementation exposes missing or contradictory design authority, it returns to Tactical Design. If it exposes missing business meaning, it returns to EventStorming.

Guard remains one fresh read-only semantic-structure reviewer. Its authority order places current BC Architecture and ready Tactical Design below Models, ready EventStorming, and accepted project constraints, but above House Style defaults and code evidence. It independently reconstructs the scoped Model projection and compares it with Codify's navigation map; the producer map is neither authority nor a verdict. Its finite units are seeded by all governing source-backed architecture responsibilities plus changed DDD-significant declarations or wiring. Guard does not parse every Mermaid arrow or create units per projection entry, arrow, file, method, layer, mechanism, or rule.

When code contradicts an accepted Tactical Design, Guard reports a violation routed to Codify. Missing or contradictory business authority routes to EventStorming; missing or contradictory collaboration-design authority, or an implementation need that changes the design, routes to Tactical Design. Existing `clear`, `violation`, and `evidence_gap` terminal states remain unchanged.

A clear Guard review with a complete snapshot-bound producer checkpoint closes every reviewed ready EventStorming and Tactical Design record together while leaving BC Architecture current. When no Tactical Design governed the implementation, EventStorming-only closure remains valid. Partial closure is rejected because it would claim that one part of the accepted iteration was implemented independently.

## Consequences

- Business behavior becomes inspectable at each Aggregate Root without turning Models into code designs.
- Command-to-Capability traceability guides Domain method design without multiplying capabilities by state branch or forcing a one-method signature rule.
- Business-required Event-to-Command causality remains current without a Reaction Policy abstraction or implementation wiring.
- Bounded Context ownership and receiver-visible Public Method collaboration become visible and confirmable before code is written.
- The same typed relationships remain traceable through Tactical Design, Codify, and Guard without a second long-lived model.
- Role authorization, local Domain Events, published contracts, Integration Messages, and event-triggered Commands no longer collapse into one generic handler edge.
- Tactical Design returns one settled Model problem rather than bouncing through one EventStorming record per question.
- Routine changes retain the low-cost direct Model-to-Codify path.
- Tactical Design records remain iteration-scoped; only their durable BC-owned decisions survive in optional sibling Architecture files, with no root architecture catch-all.
- A ready transition with no Architecture write now means every claim was explicitly justified as iteration-only; an explicit removal may still delete a file whose final current row was retired.
- Guard gains design fidelity without another reviewer, another verdict axis, arrow auditing, test execution, or file-by-file review.

## Verification

- Release contracts assert Aggregate Capability projection, Role permission persistence, BC-grouped Public-Method Tactical Design sequences, exhaustive claim disposition, temporary Codify projection mapping, independent Guard reconstruction, conditional routing, lifecycle and claims, and joint closure.
- A Tactical Design producer fixture confirms an exact draft and requires the matching ready record plus owning BC Architecture file to be written together.
- A Guard behavior fixture binds one accepted claim to a concrete Application symbol and requires code drift to route to Codify.
- Claude and Codex skill and template bodies remain mirrored, and standard release validation remains green.
